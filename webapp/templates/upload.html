Preparing the model

The network

The model must be exported to the ONNX format, with its inputs and outputs in the same order as the measures and the output events declared in the specification. For a model trained in PyTorch, consult this page for more info.

Writing a SLEEC specification

The specification

A specification is made of blocks, each opened and closed by its own keywords. On any line, everything after // is a comment and is ignored.

  • def_start … def_end — what exists: the events, measures and constants the rules refer to. Required.
  • rule_start … rule_end — the rules to verify. Required.
  • relation_start … relation_end — facts true of every input the system can observe. Optional, but without them the verifier may answer with a situation that cannot occur.

Declarations

  • event <Name> — something that happens (e.g. event cmdRequired). One event triggers the rules, and one is declared per network output (e.g. event outputSlower).
  • measure <name>: numeric or measure <name>: boolean — a quantity the rules read (e.g. measure v1X: numeric).
  • constant <NAME> = <integer> — a named threshold (e.g. constant closeAhead = 30). Values are whole numbers.

Two conventions tie the declarations to the network file: the measures are its inputs, in declaration order, and the output events are its outputs, in declaration order.

Each numeric measure also needs the range it can take, written as two constants named after it — <name>LB for the lower bound and <name>UB for the upper (e.g. constant v1XLB = -200 and constant v1XUB = 200). That range is the region the verifier searches. A boolean measure needs none: its range is already {0, 1}.

Rules

<name> when <event> and (<condition>)
     then <event>
     unless (<condition>)
     then <event>
  • A measure is read in braces, {<name>}; a constant is named directly.
  • Every binary operation carries its own parentheses — never a and b and c (e.g. (({v1X} > justAhead) and ({v1X} < closeAhead))).
  • Negation is (not <condition>) (e.g. (not {v2Presence})).
  • unless … then … is a defeater: the exception that replaces the response while its condition holds. A rule may carry several.

Relations

Relations state the general constraints the verification must respect — what is true of every input the system can be given. They usually come from the dataset the network was trained on, and they stop the verifier from answering with an input that could never occur. Five forms apply to a single evaluation:

  • measure invariant <condition> — the condition always holds (e.g. measure invariant {egoPresence}).
  • measure imply <A> <B> — whenever A holds, B holds too (e.g. measure imply (not {v1Presence}) ({v1X} = 0)).
  • measure iff <A> <B> — A and B always hold together.
  • measure mutualExclusive <A> <B> — they are never both true.
  • measure opposite <A> <B> — exactly one of them is true.
